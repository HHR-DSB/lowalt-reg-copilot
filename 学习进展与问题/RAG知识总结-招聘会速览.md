### 两版 RAG 的核心区别（必考）

| 维度 | Simple（:8002） | 增强版（:8001） |
|------|----------------|----------------|
| 流程 | 问题 → 检索 → 生成 | 意图识别 → 查询扩展 → 多查询检索融合 → 增强Prompt → 生成 |
| LLM 调用次数 | 1 次 | 3 次（延迟约 3 倍，是精度与速度的权衡） |
| 意图识别 | 无 | LLM 分类 4 领域，低置信度走旁路跳过检索 |
| 查询扩展 | 无 | 原问题 + 3 个多角度改写，提升召回 |
| Prompt | 通用助手 | 注入领域 + 意图理由 + 强制引用标注 + 诚实声明条款 |
| 额外能力 | — | SSE 流式接口、内存版多轮对话 |

## 三、核心原理速答（面试高频，每条 30 秒内说完）

**Q1：什么是 RAG？为什么需要它？**
> 检索增强生成：先从知识库检索相关内容，注入 Prompt 再让 LLM 生成。解决纯 LLM 的四个痛点：知识时效性、私有数据不可见、幻觉问题、回答不可溯源。RAG 的回答带 sources 引用，可验证。

**Q2：Embedding 和向量检索的原理？**
> 文本经 embedding 模型映射为高维向量（本项目 1024 维），语义相近的文本在向量空间距离近。检索时把问题也向量化，用相似度度量（余弦/内积/L2）找最近邻。Milvus 用 IVF_FLAT 索引做近似最近邻搜索，牺牲极小精度换大幅速度提升。

**Q3：Hybrid 混合检索是什么？为什么比单一检索好？**
> 向量检索抓语义（"打官司要多少钱" ≈ "诉讼费用"），关键词检索抓精确匹配（法条编号、专有名词）。混合检索把两者结果按权重融合（如向量 0.7 + 关键词 0.3），互补短板。

**Q4：为什么要查询扩展和意图识别？**
> 用户提问往往表述单一，一次检索召回有限。查询扩展用 LLM 从多角度改写（我实测中 3 条扩展分别覆盖了法条的不同款），多查询结果去重融合，显著提升召回覆盖。意图识别则判断问题领域，低置信度时直接走 LLM 旁路，省掉无意义的检索。

**Q5：为什么意图识别用 temperature=0.1，查询扩展用 0.7？**
> 分类任务要确定性——同一问题应稳定归到同一领域；而扩展要多样性——希望生成不同角度的改写。同一系统里不同环节对随机性的需求相反，这是 temperature 的工程理解。

**Q6：切块（chunking）为什么重要？**
> 切块粒度决定检索质量的上限：太长则语义稀释、相似度不精；太短则上下文断裂、答案缺信息。本项目 md 按标题切分 + 截断 300 字，我知道它的局限（信息截断），下一步计划做滑动窗口 + 重叠切块。

**Q7：RAG 和微调（Fine-tuning）怎么选？**
> 知识频繁更新、需要溯源、数据量大 → RAG；要改变模型风格/格式/领域语感 → 微调。两者不互斥，可组合。RAG 成本低、可即时更新知识库，是绝大多数企业知识库场景的首选。

## 四、三个最有含金量的实战故事（STAR 法则，讲 2 分钟）

### 故事一：双 bug 叠加诊断（调试方法论）
- **S**：Simple RAG 测试时 sources 永远为空
- **T**：定位检索链路断点
- **A**：不盲改代码，先看三信号（sources 字段 / answer 引用标记 / 服务终端日志），发现是**两个症状相同的叠加 bug**：①调了不存在的 `/search` 端点（应为 `/query`）②响应字段映射错位（`content` vs `text`）。修第一个后症状不变，因为第二个 bug 产生完全相同的表现
- **R**：学到**重叠 bug 的诊断陷阱**——同症状多因，修一个没效果不代表诊断错，要沿数据流逐环节验证；且终端日志永远第一优先

### 故事二：5 处硬编码模型名（工程规范意识）
- **S**：qwen-plus 免费额度耗尽（403），Simple 版改过一次模型名，增强版又挂
- **A**：grep 全局搜索发现 **5 处散落在不同函数里的硬编码模型名**，逐一修复
- **R**：配置应集中管理（常量/环境变量），"改一处生效"是基本工程规范。这个小坑让我真正理解了为什么生产代码禁止 magic string

### 故事三：答案正确 ≠ RAG 生效（最有深度的发现）
- **S**：问"劳动合同仲裁时效"，增强版返回了完全正确的法律答案，但模型在答案里声明"未使用 [参考1]至[参考5]"
- **A**：反向核查知识库源文件，发现 law.md 是**法律服务行业商业报告**（讲律所转型、客群分析），根本不是法条库——"劳动纠纷"在文中只作为商业机会出现。检索到的全是弱相关段落，模型识别出无关后诚实弃用，用自己的参数知识作答
- **R**：三个认知升级：①**答案正确性不能作为 RAG 有效性判据**，要看答案与参考片段的真实对应（我称之为第四信号）；②Pipeline 各环节完美运转，瓶颈可能在数据——**语料质量是 RAG 的上限**；③增强版 Prompt 里的"诚实声明条款"防住了假引用，这是 Prompt 工程的实际价值——同问题在无此条款的 Simple 版上，模型就硬把行业报告当依据用了

## 五、调试方法论（可迁移能力，面试官爱听）

**RAG 链路排查四信号**（我总结的）：
1. `sources` 为空 → 检索环节断（端点路径/字段映射/向量库连接）
2. `answer` 无引用标记 → 生成环节问题（Prompt 没约束引用）
3. **服务终端日志** → 永远第一现场（网络错误、403、超时都在这）
4. **答案内容 ↔ 参考片段对应关系** → 检索质量是否真正支撑了答案（防"假 RAG"）

**实验设计意识**：
- 对照实验：同一问题分别在 Simple/增强版上跑，控制变量对比
- 消融实验（ablation）：关掉意图识别/查询扩展开关，观察行为退化，量化每个模块贡献
- 反向验证：不信任表面现象，去查源文件验证假设（故事三）

## 六、可能被追问的问题（提前备好）

**"项目数据量这么小，有什么意义？"**
> 这是学习项目，重点是把全链路原理吃透并亲手踩坑。我了解生产级差异：切块策略、Rerank 重排序、评估体系（RAGAS）、并发与缓存。小数据量反而让我能逐条观察检索结果的细节。

**"你的下一阶段计划？"**
> 短期：PDF 解析入库（pymupdf + 滑动窗口重叠切块）、Rerank 重排序、RAGAS 评估；中期：把项目转化为自己科研领域（无人机辅助移动边缘计算）的文献知识库助手，喂入自己的论文和领域文献；长期方向是 Agent 开发——RAG 是 Agent 的核心工具之一，后续学 Function Calling / ReAct / MCP。

**"Docker 部署遇到过什么问题？"**
> MinIO 镜像直接拉取失败（网络限制），通过更换镜像 tag 解决；理解了 Docker Compose 编排、数据卷持久化（`down` 不删数据 vs `down -v` 删库）、健康检查预热（90 秒 starting 属正常）。

**"为什么用 Milvus 不用 FAISS？"**
> Milvus 是数据库形态：支持分布式、混合检索、元数据过滤、有 Attu 可视化；FAISS 是库，适合单机嵌入式场景。生产知识库需要的是前者。（也了解 milvus-lite 无 Windows 版本的坑）
