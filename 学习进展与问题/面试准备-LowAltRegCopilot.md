## 一、30 秒介绍（背熟，第一优先级）

> 我在四川省低空空域运行服务中心实习时发现，业务上频繁要跨多份法规查条款——民航局规章、地方条例、省级规定，措辞还不统一。回来后我独立做了一套 RAG 问答系统：多源语料入库（含扫描件 OCR）→ Milvus 混合检索 → 两阶段精排 → 带出处引用的生成。做完后我做了消融实验，发现查询扩展单独用反而降命中率，rerank 才是最大增益点——Top1 命中率从 44% 提到 78%，10 问验收 0 幻觉。项目已开源在 GitHub。

结构：痛点（实习真实业务）→ 方案（一句话全链路）→ 反直觉发现 → 数字收尾。

## 二、项目全流程（5 步）

被问"具体是怎么做的"时，按这 5 步讲：

### 1. 语料提取（三路）

| 语料                               | 提取方式                                                                    |
| ---------------------------------- | --------------------------------------------------------------------------- |
| 民航局规章 CCAR-92、川运行规则     | PDF 文字层直接提取（PyMuPDF）                                               |
| 《无人驾驶航空器飞行管理暂行条例》 | 曲线化 PDF（无文字层，内容是矢量图形）→ 渲染成图 → 多模态 OCR → 按页缓存 |
| 四川省低空规定                     | 政府网页 HTML 存档 → BeautifulSoup 解析正文容器                            |

### 2. 清洗与切块

- 噪声过滤：页码、页眉（整行相等判定）、表格残留
- 章节感知切块：滑窗切分 + 章标题偏移映射，每个切片带 `source`（哪份法规）+ `section`（哪一章）元数据

### 3. 向量化入库

- Embedding 模型 1024 维向量 → 写入 Milvus 集合 `lowalt_reg_kb`
- 共 **236 条切片**；`source` 判重保证幂等（重复执行不会重复入库）

### 4. 检索与重排（核心）

- **召回**：hybrid 混合检索 = 0.7 × 向量相似度 + 0.3 × 关键词匹配
- **放大**：召回 top_k × 4（先保证候选覆盖）
- **精排**：rerank 模型以**原始问题**为唯一基准对候选统一打分，取 top5
- 意图识别（法规类/通用类）+ 查询扩展（默认关，见深层问题）

### 5. 生成与引用

- LLM 生成答案，Prompt 含**诚实条款**：禁止虚构条文编号、信息不足时拒答优于编造
- 每个回答标注出处：来源文件 + 章节，可人工核对

## 四、面试官可能问的问题

### 浅层（明天最可能问的）

**Q：这项目是做什么的？**
→ 用 30 秒介绍（第一节）。

**Q：你用了什么技术？**
→ 报技术栈表：Python + FastAPI 服务、Milvus 向量库做混合检索、百炼的 qwen 系列模型做生成/向量化/精排、扫描件用多模态 OCR。

**Q：为什么要做这个？**
→ 实习时亲眼看到业务痛点：跨 4 份法规文件查条款，民航局/国务院/省级文件措辞不统一，人工翻很慢。实习结束就把积累的领域知识工程化了。

**Q：做了多久？一个人做的？**
→ 独立开发，约 2 个月（含学习 RAG 原理的时间）。从语料处理到服务部署全链路都是自己做的。

**Q：有什么效果？**
→ 三个数字：Top1 命中率 44%→78%，Top3 67%→100%，10 问验收 0 幻觉 0 假引用。GitHub 上有完整 README 和消融数据。

### 中层（遇到技术面试官）

**Q：RAG 是什么？为什么不直接问大模型？**
→ 检索增强生成：先从知识库检索相关内容，再让 LLM 基于检索结果回答。法规更新快、术语专业，通用大模型不知道"第三十四条"具体内容，直接问必然幻觉。RAG 让回答有据可查、可溯源。

**Q：混合检索是什么？为什么 0.7 + 0.3？**
→ 向量检索管语义（"对头相遇"能匹配"相向飞行"），关键词检索管精确术语（条文编号、专有名词）。0.7/0.3 是语义为主的权衡，法规查询里语义匹配占主导。

**Q：为什么要 rerank？一阶段检索不行吗？**
→ 召回阶段向量分数是"查询与文档的表面相似度"，不等于"文档能不能回答这个问题"。rerank 模型专门做查询-文档相关性打分，更准。两阶段 = 先广撒网（×4 召回）再精挑（rerank）。典型案例：一道题正确文档在召回里排第 7（分数 0.384），rerank 后直接第 1（0.994）。

**Q：怎么保证模型不瞎编？**
→ 三层：① Prompt 诚实条款——禁止虚构条文编号，信息不足必须拒答；② 答案强制带出处（来源+章节），可人工核对；③ 检索不到就不硬答。10 问验收里包括故意的超纲题，模型正确拒答。

**Q：遇到最大的困难？**
→ 讲 reload 坑：改完代码 rerank 始终不生效，服务看起来还活着。最后定位是 uvicorn 热重载进程扫描 Milvus 的 Docker 数据卷，遇到动态消失的文件就崩了，worker 成孤儿进程跑旧代码。修复后正常。教训：无声失败比报错更危险。

### 深层（备用速查，大概率用不上）

**Q：为什么不用 LangChain？**
→ ① 学习目的：要理解每个环节，框架把分数融合、召回稀释全封装了；② 消融实验需要直接控制检索层（放大倍数/融合逻辑/打分基准）；③ 不排斥框架——理解底层后用框架反而更快。

**Q：查询扩展为什么默认关？**
→ 消融数据：9 题 Top1 命中，基线 4/9，仅开扩展 3/9（不升反降），仅开 rerank 7/9。根因：扩展查询与它自己召回的文档措辞匹配，朴素分数融合下挤掉正确答案。不是"扩展没用"，是"这套融合机制下净收益为负"——正确做法是扩展的召回也送 rerank 统一打分，这在 Roadmap 里。

**Q：怎么评估的？**
→ 三层：消融四象限（检索质量）、10 问人工验收（端到端）、0 幻觉 0 假引用（安全性）。承认局限：人工小集不是统计显著的 benchmark，RAGAS 自动评估在计划中。
